# tgnews — Telegram-бот «новостной редакции»

Бот, который собирает посты из публичных Telegram-каналов-доноров, переводит их
на русский в стиле заданного новостного канала (эмодзи-маркер + жирный лид +
нативные телеграм-цитаты) и выдаёт администраторам по запросу — командой `/get`.
Понравившиеся посты админы отправляют в общий чат отбора для доработки и
публикации. Никакой бесконечной ленты — только готовые к редактированию посты.

```
каналы-доноры (публичные TG-каналы)
        │  realtime + бэкфилл истории (Telethon, юзербот)
        ▼
┌─────────────────────────────────────────────┐
│  один Docker-контейнер                      │
│                                             │
│  worker (Telethon)          bot (aiogram)   │
│  ─ коллектор 15+ каналов    ─ /get [N]      │
│  ─ фильтры: медиа, форварды, ─ карточки     │
│    чёрный список, дедуп       модерации     │
│  ─ рефреш метрик/подписок   ─ перевод (LLM) │
│  ─ релей медиа в канал      ─ чат отбора    │
│    Q Relay (#Q<qid>)                        │
└─────────────────────────────────────────────┘
        │                                  ▲
        │ file_id relay (без перезаливки)  │ /get
        ▼                                  │
   бот @your_bot  ────── посты ─────── админы в личке
                                          │ кнопки
                                          ▼
                              чат «отбор» (общий, для доработки)
```

## Как это работает

1. **Сбор.** Юзербот (твой Telegram-аккаунт, Telethon) слушает каналы из списка в
   реальном времени и добирает последние посты при старте. Фильтры при сборе:
   посты без текста, репосты чужих каналов, чёрный список (спорт-результаты,
   реклама, лайфстайл), дедуп Jaccard-фингерпринтом.
2. **Ранжирование.** `/get` выдаёт топ из окна 24 часа по нормированным метрикам:
   *просмотры относительно аудитории канала* × *вовлечённость (реакции/просмотры)*
   × *свежесть* (полураспад 12ч). Мелкий канал с жирным постом поднимается выше
   гигантов. Метрики (просмотры/реакции) воркер перечитывает каждые 10 минут —
   пост, собранный в момент публикации, не остаётся с нулём.
3. **Перевод.** При `/get` топ-N постов прогоняется через LLM: чистый
   «перевод + форматирование», без пересказа. Прямая речь — только прямой речью,
   оформляется нативной телеграм-цитатой (`<blockquote>`, длинные цитаты —
   сворачиваемые). Реклама и не-новости модель отбраковывает словом `SKIP`.
   Основная модель + автоматический фолбэк.
4. **Доставка.** Пост приходит админу в личку с ботом: медиа из первоисточника
   (без перезаливки, через file_id relay) + переведённый текст + через пустые
   строки голая ссылка на источник. Под постом карточка модерации:
   **[В отбор] [Отказ]**.
5. **Отбор.** «В отбор» копирует пост в общий чат (все админы + бот) с пометкой
   «Добавил: @admin» — там его дорабатывают и публикуют руками. Решения
   сохраняются, отклонённое не предлагается повторно.

## Что нужно

- VPS с Docker + Docker Compose (хватит 1 vCPU / 2 GB RAM)
- Telegram-аккаунт под юзербота (тот, на котором сканируешь QR при настройке)
- Бот: создай в [@BotFather](https://t.me/BotFather), забери токен
- Ключ доступа к LLM-провайдеру (OpenAI-совместимый `/responses` или
  `/chat/completions`) — по умолчанию настроен [opencode](https://opencode.ai)

## Установка

```bash
git clone https://github.com/izislesar/tgnews.git && cd tgnews
cp .env.example .env && nano .env   # заполнить (см. таблицу ниже)
docker compose build
```

Логин юзербота (один раз): команда покажет QR — отсканируй его телефоном,
где залогинен нужный аккаунт (Telegram → Настройки → Устройства → Привязать
устройство). Сессия сохранится в `data/` и переживёт перезапуски.

```bash
docker compose run --rm -it app python -m app.qrlogin
```

Запуск:

```bash
docker compose up -d
docker compose logs -f
```

При старте воркер сам создаст скрытый канал-релей **Q Relay** (для передачи
медиа боту), подпишется на каналы из `channels.txt`, доберёт историю и начнёт
копить метрики.

### Настройка чата отбора

Создай обычный групповой чат, добавь туда бота и всех админов, затем напиши
**внутри этого чата**:

```
/set_approval_chat
```

Готово — одобренные посты будут падать туда. Либо пропиши `APPROVAL_CHAT_ID`
в `.env`.

## Команды бота

| Команда | Что делает |
|---|---|
| `/get [N]` | выдать посты: топ за 24ч, этому админу раньше не показанные |
| `/add_channel @user` | добавить канал-донор (публичный) |
| `/delete_channel @user` | убрать канал из работы |
| `/list_channels` | список доноров |
| `/stats` | очередь + таблица источников + сводка фактчекинга |
| `/fc <qid>` | показать вердикт проверки; если проверки не было — поставить в очередь (можно ответом на карточку) |
| `/set_approval_chat` | назначить текущий чат чатом отбора |
| `/help` | справка |

Команды работают только у админов из `ADMIN_IDS` и только в личке с ботом
(кроме `/set_approval_chat`).

## Стиль публикаций и фильтры

- **`prompt.txt`** — системный промпт LLM: правила перевода, палитра
  эмодзи-маркеров, формат цитат, правила SKIP. Форматирование постов задаётся
  здесь же. После правки — `docker compose restart`.
- **`app/worker.py` → `BLACKLIST`** — чёрный список тем (регэкспы, проверяются
  при сборе, ноль токенов). По умолчанию: спорт-результаты, реклама/промо,
  гороскопы/лайфстайл. Крипта и знаменитости-ньюсмейкеры — публикуются.
- **`channels.txt`** — стартовый список доноров, сидируется в БД при первом
  запуске; дальше список живёт в БД и управляется командами бота.

## Фактчекинг по открытым источникам

Модуль `app/factcheck/` проверяет утверждения поста по внешним источникам и
ставит дисклеймер, если core-факты не подтверждаются.

Режим задаётся `FC_ENABLED`:

| Режим | Поведение |
|---|---|
| `off` | фактчекинг выключен, очередь не наполняется |
| `shadow` | при сборе посты ставятся в очередь, вердикты пишутся в БД; **в текст поста метка не идёт** — смотреть через `/fc` и `/stats` |
| `on` | при сборе посты ставятся в очередь; в карточке `/get` показывается метка, а если проверка догнала уже выданную карточку — текст карточки обновляется |

В карточке поста есть кнопка **«Проверка»**: запускает глубокий вариант (`t2`,
до `FC_CYCLES` циклов) и показывает утверждения, источники и метку.

Пайплайн: **claims → search → fetch → judge**, в 2–3 цикла:

1. `claims.py` — LLM вытаскивает атомарные утверждения (`numeric/date/event/quote/attributed/opinion`) и делит их на `core/secondary`.
2. `searxng.py` — поиск через self-hosted SearXNG (JSON API), кэш запросов 1 ч, резервные движки при `suspended`.
3. `fetch.py` — загрузка страниц с SSRF-защитой, `trafilatura` + фолбэк на абзацы; из статьи выбираются сниппеты вокруг терминов + всегда лид.
4. `judge.py` — судья возвращает строгий JSON: `supported/partial/contested/not_found/refuted`, уверенность, индексы использованных сниппетов. Ссылки на источники берутся только из реально выданной выдачи — выдуманные URL отбрасываются.
5. `policy.py` — независимость источников (нужны **разные группы издателей**; одно сообщение агентства считается достаточным), пороги, текст дисклеймера.

Дисклеймер собирается **кодом**, не моделью:

| Статус core-утверждений | Пометка |
|---|---|
| всё подтверждено | нет |
| частично / ничего не нашли | `⚠️ Не подтверждено независимыми источниками: «…»` |
| источники расходятся | `⚠️ Источники расходятся: «…»` |
| опровергнуто | `🚫 Источники опровергают: «…»` |

Если поиск лёг (все движки в `suspended`), ставится `degraded`: метка **не**
ставится, потому что «не смогли проверить» — не то же самое, что «не подтверждено».

Пайплайн запускается фоном: юзербот при сборе ставит пост в `fc_jobs`, отдельная
корутина в том же процессе берёт задачи с лизом, проверяет и сохраняет вердикт.
`/get` при этом не блокируется: если вердикта ещё нет, карточка выдаётся сразу,
а метка дописывается в неё, когда проверка закончится.

### Вариант 2: переписывание под корректные данные

Включается отдельно: `FC_FIX_FACTS=on` (работает поверх `FC_ENABLED=on|shadow`;
в `shadow` переписанный текст считается и сохраняется, но в пост не идёт).

Что происходит: если core-факт поста опровергнут или расходится с источниками,
пост **переписывается** под корректные данные, а рядом с исправленным фактом
появляется атрибуция: «…погибли 12 человек (по данным Reuters)». Стиль, эмодзи,
цитаты и структура сохраняются; пост не превращается в разбор ошибок.

Источники для правок — **только независимые СМИ**: агентства, качественные
издания, независимые российские/украинские/региональные медиа и аналитические
центры. Государственные СМИ и официальные органы (`ru-state`, `ua-state`,
`cn-state`, `tr-state`, `official`, `*-official`) к исправлению фактов **не
допускаются** — списки групп в `app/factcheck/policy.py`.

Предохранители (все обязательны):

1. правится только `core`-факт (числа, даты, события, атрибуция), не мнения;
2. вердикт судьи `refuted/contested/partial` с уверенностью ≥ `FC_FIX_MIN_CONF` (0.7);
3. независимых изданий: минимум два разных (группа не важна), либо одно агентство;
4. `source_url` в каждой правке обязан быть из уже собранных evidence — выдуманные
   ссылки отбрасываются, и если после отбраковки правок не осталось, переписывания нет;
5. переписанный текст проходит проверку длины (0.4–3× исходного) и очищается от
   служебных маркеров;
6. если правильного значения в источниках нет — `changed=false`, пост остаётся
   как был, и работает обычная метка-дисклеймер.

Исправленные факты больше не дают метку «не подтверждено»: они уже исправлены.
Если в посте остались неподтверждённые core-факты — метка ставится по ним.

Что видит админ: в карточке уже переписанный текст; по кнопке «Проверка» — список
«было → стало» с указанием источника. В `shadow` карточка остаётся исходной,
а правки видны только в проверке (для калибровки).

Проверить пост вручную:

```bash
# локально, с .env и поднятым SearXNG
SEARX_URL=http://127.0.0.1:8888 PYTHONPATH=. .venv/bin/python -m app.factcheck.cli \
  --db data/queue.db --qid 349 --env-file .env --tier t2

# с переписыванием под независимые источники
... --fix

# машинный вывод
... --json
```

`--tier t1` — один цикл (дешево), `t2` — до `FC_CYCLES` циклов и нейтральность.

Основные переменные: `FC_ENABLED=off|shadow|on`, `SEARX_URL`, `FC_CYCLES`,
`FC_MAX_CLAIMS`, `FC_DEADLINE_S`, `FC_CALLS_PER_POST`, `FC_TOP_HITS`,
`SEARX_FALLBACK_ENGINES`. Полный список — в `.env.example`.

SearXNG поднимается сервисом `searxng` в `docker-compose.yml` (настройки —
`searxng/settings.yml`, JSON-выдача включена). Движки Google/DuckDuckGo с
датацентрового IP периодически уходят в капчу — поэтому нужен `SEARX_FALLBACK_ENGINES`
(по умолчанию `bing`) и запас по времени.

Список доверенных издателей и их групп — `PUBLISHER_GROUPS` в `app/factcheck/policy.py`.
Незнакомый домен попадает в группу `other` и **не** считается подтверждением:
список надо пополнять (в выводе CLI он виден как `other`).

## Эксплуатация (production)

**Живость.** У обоих контейнеров есть healthcheck: у `app` — heartbeat-файл
`/tmp/health` (обновляется раз в минуту), у `searxng` — `/healthz`.
`docker compose ps` показывает `healthy`; если `app` ушёл в `unhealthy`,
`restart: unless-stopped` перезапустит его.

**Память.** Лимиты: `app` — 800 МБ, `searxng` — 350 МБ (сервер 1.9 ГБ, swap нет).
Приложение держит ~500 МБ RSS (Telethon + aiogram + lxml/trafilatura), поэтому
`MALLOC_ARENA_MAX=2` и `FETCH_CONCURRENCY=2` — это сознательные настройки, не
меняй их без замера. Если `app` упирается в лимит — первым делом снижай
`FC_MAX_CLAIMS`/`FC_SNIPPETS` или выключай `FC_FIX_FACTS`.

**Расходы.** `FC_DAILY_CALLS` (по умолчанию 600) — предохранитель: при исчерпании
задачи остаются в очереди до следующих суток, бот продолжает работать. Текущий
расход виден в `/stats` («LLM сегодня: N/600»), история — в `fc_runs`.

**Ретеншен.** Раз в 6 часов удаляются: завершённые задачи старше
`FC_RETENTION_DAYS` (14), запуски `fc_runs` и `evidence`.

**Бэкапы.**

```bash
# разовый
bash deploy/backup.sh
# ежедневно в 04:00 UTC
cp deploy/backup.sh /root/tgnews/deploy/backup.sh
cat >/etc/systemd/system/tgnews-backup.service <<'EOF'
[Unit]
Description=tgnews sqlite backup
[Service]
Type=oneshot
ExecStart=/root/tgnews/deploy/backup.sh
EOF
cat >/etc/systemd/system/tgnews-backup.timer <<'EOF'
[Unit]
Description=tgnews backup timer
[Timer]
OnCalendar=*-*-* 04:00:00
Persistent=true
[Install]
WantedBy=timers.target
EOF
systemctl daemon-reload && systemctl enable --now tgnews-backup.timer
```

**Включение фактчекинга.**

| Шаг | Команда | Что меняется |
|---|---|---|
| 1. Обкатка | `FC_ENABLED=shadow` (+`FC_FIX_FACTS=on`) | вердикты и правки считаются, посты не меняются |
| 2. Проверка качества | `/fc <qid>`, `/stats` | смотрим долю опровергнутых и качество правок |
| 3. Боевой | `FC_ENABLED=on` | метки и переписанные тексты идут в карточки |

После правки `.env` — `docker compose up -d --force-recreate app`.

**Откат.** `git reset --hard <предыдущий-коммит> && docker compose up -d --build`
на сервере; для отключения только фактчекинга — `FC_ENABLED=off` и рестарт `app`.

**Безопасность.** Контейнер `app` работает под non-root (`uid 1000`), поэтому
`data/` должен принадлежать `1000:1000`: `chown -R 1000:1000 data`. Приватный
deploy-ключ вынесен из тома приложения (`/root/keys-backup`), `.env` — `0600 root`.
Секреты в образ не попадают, `prompt.txt` берётся из образа, но может быть перекрыт
bind-mount'ом.

**Диагностика.** `docker compose logs --since 1h app | grep '\[fc'` — прогресс,
`[fc.fetch] HTTP 403` у отдельных доменов нормален (антибот), `[fc] цикл qid=…` —
единичные ошибки, после 3 попыток задача уходит в `error` и админам приходит алерт.

## Ограничения (честно)

- Доноры — только публичные каналы; юзербот должен иметь доступ
  (каналы ботоподпиской не читаются).
- Кросс-языковой дедуп (та же новость с арабского и английского доноров)
  не ловится — Jaccard работает внутри одного языка.
- Юзербот на личном аккаунте: чтение каналов и постинг в релей — обычная
  активность, но аккаунт — единая точка отказа. Признаки логаута в логах:
  `AuthKeyDuplicated` / `Unauthorized`.
- Перевод идёт последовательно: `/get` с медиа занимает до пары минут.
- Фактчекинг проверяет только то, что есть в открытом вебе: события последних
  часов (особенно цифры потерь и «кто что обстрелял») часто не подтверждаются,
  и метка «не подтверждено» будет на них ставиться. Это ожидаемо: метка значит
  «мы не нашли подтверждения», а не «это ложь».
- Качество проверки ограничено поисковой выдачей: движки SearXNG периодически
  уходят в капчу, а неизвестные домены не считаются подтверждением.
- Фоновый режим тратит один вызов LLM на пост уже при сборе (`t1`). При 300+
  постах в сутки это заметно: ограничители — `FC_CALLS_PER_POST`, `FC_CYCLES`
  и ручной `FC_ENABLED=shadow` на период обкатки.

## Частые проблемы

| Симптом | Причина / решение |
|---|---|
| `Сессия worker'а не авторизована` | пройти `python -m app.qrlogin` заново |
| `BOT_TOKEN пуст` / `ADMIN_IDS пуст` | заполнить `.env`, `docker compose up -d --force-recreate` |
| Посты без медиа, хотя в доноре картинка | релей не готов: проверь логи `[relay]`, канал Q Relay существует, бот — админ |
| Все посты `dead` | слишком строгий промпт: модель уходит в SKIP — смягчи правила в `prompt.txt` |
| В выдаче мусор не по теме | дополни `BLACKLIST` в `app/worker.py` и/или правило 8 в `prompt.txt` |
